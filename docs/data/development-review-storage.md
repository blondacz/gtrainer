# Development review storage foundation

The development review store is an explicit, separate SQLite database path and never derives its location from personal application configuration or environment variables. The launcher/store must be configured to use a new owner-only local path. Existing databases are checked through a read-only connection before any write or permission change and are accepted only when both the SQLite application ID and private schema marker match; unrelated databases are refused without changing their bytes or their parent directory permissions. No personal database migration or import is performed.

Only `cases-v2.json` is packaged as fixture data. Its SHA-256 is pinned in code and fixture identifiers are resolved server-side; packet text and paths are not inputs to preview creation. A preview binds the exact fixture packet, prompt digest, structured explicit model settings and configured development-policy budgets. SQLite persists previews, submitted runs, ordered queue rows and durable events with compare-and-set claim/publication/failure and immutable creation/24-hour expiry. Expired payload is hidden on inspection; reads do not sweep or delete. Capacity counts all physically retained previews, even expired ones; a preview/run pair consumes one slot. Preview creation does not submit work or create a wake-up event. Queue admission, queued-only supersession, ownership/recovery fencing, explicit cancellation, exact stop receipts and bounded event-triggered retention cleanup are implemented. See `development-review-queue.md` and `development-review-worker.md` for separate creation/TTL rules and the elected pipeline.

The private schema marker is `gtrainer-development-review-v3`. Earlier incomplete schemas without immutable policy bindings and separate submitted-run identity are rejected rather than silently migrated. Compatible v3 development stores receive additive, idempotent owner/safety/runtime/event/diagnostic tables on open; this does not advance the owner epoch, sweep retention or migrate personal storage. Owner epochs and minimal safety records have no payload foreign key. See `development-review-ownership.md` for election and recovery. Store operations synchronize per instance and use bounded `IMMEDIATE` SQLite transactions to serialize writes across connections. Named repository SQL and shared binding/transaction/resource helpers keep query values parameterized. Storage failures carry only `development_storage_unavailable`, without driver causes or SQL; failure reasons are allowlisted, not accepted because they resemble a safe identifier.

New database files and dedicated containing directories require owner-only POSIX permissions; existing target files/directories must already meet that policy. SQLite uses delete journaling and runs in a restricted directory; transient journal auxiliaries are protected by that directory. Unsupported or failed permission enforcement refuses operation. Permissions and row deletion cannot guarantee forensic erasure. Filesystem snapshots, backups, copy-on-write storage, SSD wear levelling and previously copied data may retain remnants. Operators must use a dedicated local directory and avoid backup/snapshot policies that capture this data.
