# Design

## Context

See proposal.md for motivation. `ConnectedReviewProvider` already abstracts generation and `ConnectedReviewExecutor` owns whole-draft validation, packet bindings, two attempts, monotonic deadlines and a default-closed execution gate. `ConnectedReviewService` composes production qualification and hosted consent; normal `Application.kt` supplies an empty catalogue. Existing `/run` is synchronous and `ConnectedReviewPanel.tsx` waits for it. None of that authorizes production calls.

`ConnectedReviewExecutionLimits` currently caps attempts at 600 seconds and totals at 1200 seconds. Its default input/output ceilings are 32/12 KiB; `InterpretationContractV1.decodeDraft` also caps draft text at 12,000 characters. These are not the Pi V3 benchmark's 24 KiB response ceiling. Existing local adapters implement restricted endpoint selection, runtime/tag/digest checks and bounded envelope reads, but use different wire contracts. Mac inference is reachable at loopback port 11435, outside the older adapter's allowlist.

The nine `benchmarks/connected-review/cases-v2.json` packets are frozen synthetic inputs with explicit IDs and source dates. Existing personal snapshot storage expects contexts from its own database. Development must use a separate database, never insert synthetic entries into personal persistence. `HistoryService.sync()` currently performs explicit API-request imports under a mutex, not a background import worker. Import execution and the existing production review queue are outside this change.

The initial plan was blocked because Ollama `/api/ps` reports model residency, not authoritative active/queued generation. The user approved a dedicated runtime-owning worker, a durable queue, 24-hour expiry from creation, queued-only supersession on newer input and inference-worker-owned cleanup. Cleanup/reconciliation are phases of normal task processing, with an optional explicit maintenance-only task. There is no idle TTL timer, periodic housekeeping wake-up or unconditional startup retention sweep.

## Goals / Non-Goals

**Goals:**
- Exercise the real provider and existing validator against fixed synthetic inputs through the dashboard, without a production bypass.
- Keep model choice, generation settings and slow-runtime deadlines operator-configurable but immutable per run.
- Make queue history durable and distinguish accepted cancellation, confirmed process termination and payload deletion.
- Co-locate execution and retention ownership while allowing short API transactions to accept new work and cancellation concurrently.

**Non-Goals:**
- Personal-data inference, hosted adapters, qualification, automatic benchmark completion or changing the frozen evaluation rubric.
- Model downloading, live deployment, takeover of existing runtimes, automatic cross-node failover or scheduled task creation.
- Adding an import worker, changing personal persistence, or sharing the development worker with private imports.
- Streaming partial interpretation text, arbitrary browser prompts or generalized cluster administration.

## Decisions

### 1. Separate launcher and durable development repository

Add a dedicated development entry point and explicit Gradle launch task. Its browser-facing server binds only to `127.0.0.1`, requires an operator enable flag and separate session/CSRF credentials, and serves only development APIs plus the frontend shell. Reuse security helpers without calling normal `environmentConfiguration()` or constructing `HistoryService`/`HistoryStore`. Do not inherit private database/source credentials. Production entry points never expose development routes. Worker service access from the Mac uses authenticated, explicitly configured private access/tunnelling, not public ingress.

Implement a dedicated SQLite repository using existing JDBC dependencies and a configured owner-only development path/local PVC, never the personal database path or environment variable. Persist immutable previews/packets, provider/generation/policy bindings, runs, ordered queue entries, attempts, ownership epochs and cleanup receipts. Transactions enforce compare-and-set outcomes and capacity: at most 32 retained previews/runs plus small safety/control records. Reject excess submissions rather than evicting active/queued work. Load only bundled, hash-checked synthetic fixtures; browser requests name cases, not packet contents or paths. Verify all nine packet fixtures against the frozen source. Queued work survives restart; claimed/uncertain work is never replayed. Alternatives: memory-only storage loses inspectable history; a production database mixes privacy scopes; Redis/distributed queues are unnecessary for one worker.

### 2. Dedicated Ollama adapter with explicit catalogue

Add `OllamaConnectedReviewProvider` implementing the existing provider interface. Operator-only configuration supplies provider/model IDs, label, tag, digest, Ollama version, context window, token ceiling, threads, seed and temperature. No defaults pick a model. Within the dedicated Linux container, Ollama binds only to `http://127.0.0.1:11434`; only the runtime-owning worker can call it. Do not expose a direct Ollama Service or adopt the existing Mac port 11435/Pi runtime. Bind each call to the supervisor's exact runtime generation. Reject arbitrary endpoints, redirects and browser-supplied settings; leave older adapter policies unchanged. Models remain replaceable through explicit configuration of this owned runtime, not uncontrolled direct endpoints.

Use Ktor CIO with retries/redirects disabled, bounded version/tag reads and non-streamed, non-thinking JSON chat requests with explicit generation options and zero keep-alive. System/packet messages come from `InterpretationContractV1.prompt`; correction adds only a fixed rejection reason. Local cost is null. Require success, `done=true`, expected model identity, absent/empty thinking and non-truncated completion. Cap the envelope at 64 KiB and extracted UTF-8 draft at 12 KiB; retain the validator's 12,000-character ceiling. Never salvage partial JSON or retry transport errors. HTTP deadlines cover the attempt; the executor owns inference deadlines. Alternative: existing adapters use other contracts; an uncontrolled gateway cannot establish exclusive ownership.

Provide a disabled example for `gtrainer-qwen3:8b-q3_k_m` with 2048 context, 1536 output tokens and three CPU threads; reference the verified digest but verify it again at runtime. These settings do not guarantee every fixture fits or a useful answer: refuse oversized input and retain length-truncation/protocol failures. Show the settings and input hash for provenance. Label these runs development, not ordinary V3 or the Q3 benchmark reference.

### 3. Explicit local-development policy, with unchanged ordinary/hosted bounds

Add a named policy discriminator/factory: ordinary keeps its defaults and 600/1200-second bounds; `connected-review-development-local-v1` permits up to 900/1840 seconds. Require explicit budgets and keep two-attempt, byte and cost bounds. Reject this policy with hosted providers and in production service construction. The 1840-second ceiling is not a guarantee of two full 900-second attempts: pre-send observations and validation consume time. Queue waiting is not inference time, but persisted creation-based TTL caps the whole run's lifetime. At claim, bind a monotonic execution deadline and cap it by remaining TTL; never start expired work or reset budgets during recovery.

Expose a non-sensitive attempt observer, defaulting to a no-op for existing callers. Persist attempting/correcting metadata, never raw rejected text. Total time starts at claim, before runtime startup/preflight, and includes health/validation overhead. Persist creation/expiry in UTC and use monotonic clocks for live execution deadlines. Initial storage/ownership reconciliation has a separately bounded budget and cannot hold a long database transaction. Add fake-clock/tiny-budget tests. Alternative: extending only transport timeouts obscures executor deadlines and permits restart budget resets.

### 4. Dedicated process ownership supplies authoritative stop evidence

Package a new dedicated Linux development appliance for Pi K3s or the Mac Linux/K3s VM. A PID-1 supervisor owns the queue worker and the Ollama execution process tree, with no alternate inference client. Start a fresh Ollama process for each run, retain it through the one permitted correction, then stop it even after successful validation. Model storage persists independently. The supervisor must handle reparented/detached descendants, not merely wait for `ollama serve` or kill one process group. Worker failure triggers supervised execution-tree termination before worker replacement. Deliver disabled packaging examples; neither deploying them nor taking over the existing runtime is authorized.

The Linux boundary uses a small standard-library Python PID-1 supervisor plus a fresh per-run subreaper keeper. Kernel ancestry, pidfds and waitpid/ECHILD handle detached/reparented descendants without Java ProcessHandle/process-group assumptions or new JVM dependencies. A private Unix socket authenticates the exact sole worker PID through SO_PEERCRED. Keeper loss quarantines new starts while the healthy worker remains available; durable ownership/old-container verification still fence recovery. Test-only command injection and sleeping-child fixtures are excluded from the appliance image. The approved local Lima sandbox has a separate home, no host mounts/application forwards and no model/JVM/Ollama execution.

The supervisor holds a lifetime filesystem ownership lock and advances a durable ownership epoch. Persist claim/start intent before any request; bind publication/cleanup to run ID, epoch, container identity and runtime generation. Accept cancellation transactionally before signalling the process tree. Close the request, TERM the owned execution processes, escalate to KILL within sixty seconds, and reap/verify all execution descendants exited. Persist that receipt before allowing the next run. If stop cannot be verified, quarantine the runtime; later queue events or an explicit maintenance task retry bounded reconciliation, not inference. Model lists, HTTP disconnection, unload acknowledgements and lease expiry are never stop evidence. In-progress runs are never killed just because newer input arrives.

Pin this appliance to one configured node with local persistent storage; no automatic cross-node failover. On supervisor/container restart, fence old epochs and classify already-claimed runs as interrupted rather than replaying them. Before starting another runtime, obtain trusted evidence that the exact old container execution boundary terminated: a narrow read-only verifier on the owning healthy node checks the recorded container ID's stopped state through the container runtime, or verifies a changed host boot identity. Pod deletion, replacement readiness, replica count, RWO storage and Recreate are insufficient. Missing/unreachable evidence keeps execution blocked, while queue inspection/submission remains available within capacity. Never force-delete or reschedule around uncertainty. Alternatives: ledger-only leases cannot terminate stale computation; shared runtime recycling could kill unrelated work.

### 5. Health observation supplements ownership

The synthetic development gate verifies fixture/prompt/config bindings and ownership; it never records qualification. An observer checks the owned runtime version/model digest, container identity, readiness, expected memory ceiling and at least 1024 MiB available host memory. Require zero unexpected runtime restarts during an execution generation. Between runs, verified owned-process recycling is an intentional new generation, not a hidden continuation. On Pi, preserve the live app's readiness and unchanged restart baseline observed across ten seconds; historical app restarts are allowed.

The disabled 8 GiB Pi example allocates about 5 GiB to the whole worker/runtime container: roughly 2 GiB for OS/other processes plus 1 GiB reserved host headroom leaves about 5 GiB. JVM/supervisor overhead counts inside that allocation. These are planning estimates; the live headroom/limit observations remain authoritative and model fit is not promised. The 1 GiB non-inference test VM is a separate fixture budget, not the runtime allocation or reserve.

Use single-flight observations at five-second scheduling opportunities, with a sixty-second bound on the entire observation, not each command independently. Timestamp constituent measurements and calculate freshness from the oldest relevant one; an independent watchdog aborts if age exceeds seventy seconds. Read host data via the bounded configured node observer; keep resource command arguments fixed/validated and private data out of samples. Pre-send and publication require fresh matching evidence. Any resource failure, ownership change or unavailable health data prevents publication and invokes owned-process stop. Alternatives: health-only checks cannot prove idle; overlapping monitors create uncontrolled load.

### 6. Durable, event-driven queue and queued-only supersession

Development APIs expose configuration/cases, preview/submission, queue listing, run inspection, explicit cancellation and maintenance-only submission. Authenticate all access and CSRF-protect writes with strict small schemas. Return `202` after a short durable submission transaction, without waiting for health checks or generation. Idempotency uses immutable preview ID: duplicates return the existing run and do not change creation, expiry or budgets. Once that preview/run expires, old submissions are rejected; only a new explicit preview can create work. Unsubmitted previews also expire after 24 hours. No browser refresh, polling or restart submits new inference. Persist relevant queue events in the submission/cancellation transaction; notifications occur only after commit.

Preview and run creation are distinct: a preview starts its own 24-hour submission eligibility; first explicit submission creates a separate run ID and immutable run creation/24-hour expiry. The associated submitted payload follows the run's expiry. A preview/run pair occupies one retention slot, not two. Preview creation records no queue event; only submission can admit inference work. An expired preview identifier cannot submit again, even if its later-created run remains inspectable until that run expires.

One worker drains eligible queued runs FIFO. Persist an output-slot key and ordered input revision/digest: for this synthetic scope the slot identifies fixture case, configured provider/model and contract, so different benchmark candidates and context variants cannot supersede each other. A genuinely newer fixture input revision replaces only still-queued runs in that slot, atomically linking the supersession reason/replacement. Repeated identical input is not automatically a new revision. Lower/equal revisions cannot evict newer work. The running predecessor finishes normally; its output stays bound to its older input and must not replace the latest-input view. Input revisions are from trusted bundled fixture/catalogue versions, not browser text; frozen benchmark packets remain unchanged.

Durable queue events are authoritative; notifications merely wake their consumer. Startup first reconciles old execution boundaries, then reads pending events/tasks. It does not independently sweep retention when no event/task exists. Processing a normal task runs bounded cleanup/reconciliation, claims eligible work atomically, executes it, confirms process termination and acknowledges the corresponding event. Persist transitions/events so a crash or lost in-process notification cannot lose work: on restart or the next notification the worker re-reads pending durable events and drains eligible tasks. Do not acknowledge away pending work before its claim/terminal transition is durable. There is no idle timer/polling fallback; cleanup of expired history waits for a subsequent event. No automatic inference retry or task-creation schedule is added.

While a model runs, the same worker's event loop still handles explicit cancellation, health failures and its active execution deadline, capped by remaining TTL. It does not launch another inference or stop the running predecessor for newer input. A maintenance-only task, submitted explicitly through an authenticated API/developer command, runs the same cleanup/reconciliation phases and skips inference. It is serialized through the same owner; if a run is active it waits, except already-due explicit cancellation/safety reconciliation. Record its outcome and creation-based expiry like other tasks. Active deadline/health watchdogs remain; they are not idle retention timers. Cleanup does not hold a database transaction across process waits or network calls.

The same elected inference worker owns housekeeping, rather than a second cleanup/import worker. API writes remain concurrent short transactions; single-worker ownership is not a substitute for atomic database conditions. Publication/cancellation/supersession/expiry use one authoritative terminal transition. At publication commit check the owner epoch, deadline/expiry, latest cancellation state, immutable binding and valid health observation. Cancellation reports success only if it wins that transition; a previously successful run cannot be relabeled cancelled. Preserve existing normal APIs and stored production states.

### 7. Creation-based TTL and async cleanup without lost safety state

Persist `expiresAt = createdAt + 24 hours` for every run, regardless of outcome. Supersession/cancellation/completion never extends TTL. Check expiry before claim and publication even if no cleanup event has run. Active expiry is enforced by the run's already-existing deadline and invokes termination. On later queue-event processing, successful/failed/cancelled/superseded/expired histories and their previews, prompts, outputs, attempts and payload auxiliary records are deleted in bounded batches. Read-only inspection hides expired payload and reports expiry/deletion-pending, without initiating cleanup. Physical deletion can be later than 24 hours, including indefinitely without events; startup alone does not sweep. An explicit maintenance-only task provides ad hoc catch-up. TTL is eligibility, not an exact-second or forensic-erasure guarantee.

Move unresolved ownership into a minimal non-payload safety/control record before deleting run content. Retain opaque run/epoch/container/process-boundary identities, expiry and unresolved-stop status, never prompt/output text; remove it after confirmed stop when recovery no longer needs it. Expired runs cannot vanish with execution unconstrained. Deletion racing publication/cancellation is transactionally fenced; stale callbacks cannot recreate payload. Bound cleanup batches and failed-delete retries per event; later events or maintenance retry deletion without a cleanup-only timer. Failed deletion need not block safe inference, but failed stop does. At storage capacity, still permit a bounded/coalesced maintenance signal so expired rows cannot permanently prevent cleanup. Durable processed event records follow associated payload retention; deduplicated non-payload wake-up records cannot grow without bound. No new database backups; disclose SQLite/WAL/filesystem remnants. Alternatives: deleting rows loses cancellation targets; import-worker cleanup crosses privacy scopes.

### 8. Inspectable queue and independent status dimensions

In the isolated launcher, expose an opt-in Developer options visibility switch and special Developer tab. The normal application exposes no development queue capability; changing UI visibility never grants execution permission or submits work. The tab shows queue order, slot/revision, creation/expiry, replacement links, model/settings/budgets, runtime identity/health, attempts/timings and three distinct dimensions: logical outcome (`queued`, `running`, `successful`, `failed`, `cancelled`, `superseded`, `expired`), execution (`not_started`, `starting`, `executing`, `stopping`, `stopped_confirmed`, `unknown`) and retention (`retained`, `deletion_due`, `deleting`, `payload_deleted`, `deletion_failed`). Cancelled/stopping is not confirmed stopped. Deleted run history disappears; aggregate safety-block information remains without payload. Store only the run ID in the page URL, not browser packet storage. Read-only reconnect restores history without submission. Keep synthetic/unqualified and empty-result labels; never imply latest-input output from an older run.

Persist bounded structured worker summaries for normal and maintenance tasks: triggering event, actions/counts, affected opaque run IDs, fixed reason codes, timestamps and whether work executed, remained queued or was blocked. Render human-readable explanations from reason codes, such as expired-before-claim, queued-input-superseded, running-predecessor-preserved, cleanup-pending or runtime-stop-unconfirmed. These are code-recorded causal decisions, not model-generated reasoning or chain-of-thought. Apply run TTL to associated summaries and aggregate event summaries' own creation-based TTL; housekeeping deletes summaries alongside their eligible records. Keep only minimal non-payload fencing reasons past TTL if safety requires. Do not include prompt/context text, rejected output, credentials, raw command failures or full environment dumps. Summaries/diagnostics are authenticated read-only inspection; enabling the tab or polling never triggers cleanup or inference.

Documentation distinguishes development acceptance from qualification. Existing qualification tasks 6.2/6.3 and Q3 retry/continuation history remain unchanged. Implementation uses synthetic database tests, process-boundary tests and mocked host observers; real-host access/deployment/inference requires separate approval. Alternatives: a production override or declaring schema acceptance a qualification conflicts with existing requirements.

### 9. Apply Effective Java principles idiomatically, not mechanically

Follow up the completed generic review task 7.3 in `connected-insights-context` with an explicit Joshua Bloch *Effective Java* review of touched/new connected-review code and its integration boundaries. Apply the relevant principles: minimize visibility and mutable state, validate at construction, defensively copy nested collections at ownership boundaries, keep equality/hash contracts sound, document thread-safety/state transitions, prefer composition and small responsibility-focused types, close owned resources deterministically, and use specific failures while preserving coroutine cancellation. Kotlin `val`, data classes and read-only collection interfaces are not proof of deep immutable snapshots. Use sealed/enumerated states and validated value types where they clarify contracts; retain explicit compatibility at API/storage boundaries. Avoid blanket Java patterns, unnecessary builders/frameworks and repository-wide churn. Record concrete findings, focused regression tests and justified exceptions; no privacy/validation/qualification rule may be weakened as a refactor. This artifact update adds the review work but does not claim the code is already compliant.

## Risks / Trade-offs

Quality acceptance also covers method size and SQL ownership: split touched oversized routing/execution/persistence methods by cohesive responsibility rather than arbitrary line counts. Keep schema/migrations and named queries in the repository boundary, with parameter-bound values and controlled identifiers; extract reusable row mapping, transaction and binding helpers instead of scattering magic SQL literals or creating a giant miscellaneous query bucket. Use named constants/validated types for state, reason and policy values. Record before/after responsibility changes and justify remaining long methods/queries. Database failure responses use fixed reasons, never SQL text or raw driver messages. Regression tests verify parameter binding, atomic transitions and unchanged wire/storage contracts. These are scoped changes, not authorization to restructure unrelated work.

- [Remote computation may outlive transport/worker failure] → Exclusive supervised process tree, durable fencing/receipts and fail-closed reconciliation; never terminate shared runtimes.
- [Remote resource observation is slower or unavailable] → Bounded command deadlines, freshness limits and fail-closed status; no inference enabled from version checks alone.
- [Reduced context or slow generation still fails] → Keep settings and deadlines visible; expose failures without changing validators or automatically increasing budgets.
- [Database loss or unreachable owning node] → Block uncertain old execution; never infer stopped state from new pod readiness or replay claimed work.
- [Restarting Ollama per run adds load latency] → Persist models on disk, expose startup timing and keep loading inside budgets; warm reuse is a future separately verified optimization.
- [Same-worker cleanup could starve execution] → Short bounded transactions/batches and retry limits per event; unresolved process stop remains a hard execution block.
- [No queue events after TTL expires] → Expired work cannot execute/publish and expired payload is hidden, but physical deletion waits; an explicit maintenance-only task can trigger catch-up.
- [TTL deletion is not physical erasure] → Delete payload/auxiliary records asynchronously, avoid new database backups and disclose WAL/filesystem remnants; safety records contain no payload.
- [Bundled fixtures drift from benchmarks] → Hash and semantic parity tests; no response captures or personal files bundled.
- [More restrictive application response limits than benchmarking] → Document both profiles; do not compare acceptance rates as equivalent experiments.
- [Synthetic-only launcher is not yet useful with personal history] → Intentional scope boundary; future personal-data execution requires its own explicit decision and qualification.

## Migration Plan

This is additive development tooling with an isolated new database, worker supervision and disabled runtime packaging examples, not a live personal schema migration. Implement and test without contacting either host. Future deployment must separately authorize a new dedicated appliance, node-local storage and the narrow read-only termination verifier; never adopt or stop the existing deployment implicitly. Resource guards may refuse operation if another loaded model occupies needed headroom. An approved smoke test must validate real process-tree termination and old-container reconciliation, not only observer doubles. Rollback stops the owned appliance after verified cleanup and preserves unresolved safety records until reconciled; personal storage, existing model files/runtimes and benchmark captures remain untouched. No code or deployment is performed by this artifact update.
