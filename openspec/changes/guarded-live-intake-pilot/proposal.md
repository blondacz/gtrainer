# Proposal

## Why

The completed synthetic interaction harness proves inspect/edit/resolve/stage/confirm
boundaries only with handwritten witnesses. A separately bounded acquisition of one
real model response is the smallest next check of that path without opening personal
data, on-demand browser inference or production admission.

## What Changes

- Add a distinct synthetic live-pilot profile for one preselected, already known v5
  packet: **u02**, containing an explicit travel interval and unresolved training
  details. This is an integration experiment, not a fresh or blind quality evaluation.
- Acquire its real response through a newly authorized, source-bound durable worker,
  then stop the owned runtime and seal the raw/validation/ownership evidence before
  the loopback UI can inspect it. No browser request starts or retries inference.
- Reuse unchanged strict validation, the existing editor and explicit confirmation
  into a new disposable synthetic store. Keep handwritten-fixture and live-acquisition
  provenance distinct; do not fabricate production execution/publication receipts.
- Propose a non-renewable allowance of **at most one intake generation and one
  mandatory non-scored stop probe**, no corrections, retries, fallback, prompt revision
  or replacement run. Freeze exact settings, deadlines and cleanup authority before
  any model request. Reuse existing resource/ownership safeguards without weakening them.
- Implement and prove the path offline with fake transport first. Stop for a separate
  execution grant after checks pass. Invalid, empty, incomplete or unsafe results
  remain recorded outcomes, not reasons to generate a replacement or show a witness.
- Preserve the completed fixture harness, historical acquisition/report bytes and all
  normal application/runtime admission gates. No personal-data pilot or deployment.

## Capabilities

### New Capabilities

- `intake-extraction-evaluation`: Extend this capability from the pending v4/v5
  changes with a separately admitted, one-capture synthetic integration path and
  read-only inspection of genuine acquisition provenance. Reuse the established
  capability path rather than create a version- or experiment-named duplicate.

### Modified Capabilities

None in the published main specs. `connected-review-development` remains unchanged:
its queued API, two-attempt correction policy and runtime are not the live-intake
pilot's execution contract. This proposal does not open `ScopedProfileAdmission`.

## Impact

Proposed changes are confined to an isolated benchmark adapter/profile, focused
offline tests, test-classpath loopback integration and a separate pilot UI entry or
explicit adapter. Existing durable supervision, source-bound capture, strict Kotlin
validation and confirmation are reused; no general provider or scheduler is added.
Implementation must not edit manifest-pinned historical files to grant a smaller
run under an old suite's identity. Exact seams and proposed limits are in
[design.md](design.md); bounded acceptance slices are in [tasks.md](tasks.md).

**Material runtime gate:** the inherited worker pauses the existing Ollama
deployment (`1→0` replicas), creates and stops an owned probe pod, creates an owned
extraction pod, then restores the exact original deployment after authoritative
cleanup. These operations interrupt the shared service. They are proposed, not
authorized. If that explicit pause/restore and pod lifecycle are not approved,
live acquisition stays blocked; it must not fall back to shared-server inference.

**Current approval is planning only.** The user's “ok, do it” follows the explicit
offer to prepare this proposal. Implementation requires a new apply instruction;
actual probes, model calls and owned runtime operations require a later exact grant.
No existing database access/reset/migration, model download, VM resize, independent
service restart/takeover, publication, deployment, commit/push, spec sync or archive
is authorized. Any live runtime transition needed by inherited guards must first be
listed for approval; inability to satisfy those guards blocks execution.
